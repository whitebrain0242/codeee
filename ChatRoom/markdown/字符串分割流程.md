拿到底层字节流 → 按行切分 → 去掉首尾空格 → 把第一个单词转大写当作命令名 → 剩余部分作为参数

std::from_chars：知道它是 C++17 最快的数字转换，比 atoi 安全。下次写数字解析，记得复制它的用法。

std::string::find_first_of(" \t")：知道可以用它一次性匹配空格和制表符。

返回 Command{...} 结构体：知道解析完要封装成对象，而不是返回两个独立的字符串（这是工程规范）

1. 如果输入全是换行符？
那么还是在输入缓冲区中按照换行符切割，发现是空字符，return

2. 如果用户输入很长很长的命令，最后才输入换行符（如 10KB 的 "AAAA..." + "\n"）？
分两个阶段看：
阶段一（发送中）：客户端可能分多次 send 发完。服务端每次收到一部分数据（比如前 4KB），handleRead 就会触发，把这 4KB 追加到 inputBuffer_ 尾部。此时 inputBuffer_ 里没有 \n，业务层的 findEOL 返回 nullptr，于是业务层什么都不做（数据暂存在缓冲区）。
阶段二（换行符到达）：客户端终于发完了最后一块数据（包含那个 \n）。handleRead 再次触发，把剩余数据读入 inputBuffer_。此时业务层发现 findEOL 找到了 \n，于是取出这一整行（10KB），开始解析。
Buffer 是动态扩容的（std::vector），它会自动 resize 来容纳超长数据，不会丢失。但如果恶意用户一直不发换行符，服务端的内存会被持续消耗，所以成熟的服务器会在业务层设置 “最大消息长度限制”

3. 接受和发送的时机？
对于接收端（服务端）：
网卡收到数据包 → 内核 TCP 缓冲区有数据。

内核触发 EPOLLIN → 服务端立即调用 read 把数据全部搬走（可能一次读几KB）。

数据搬进 inputBuffer_ 后，业务层尝试找 \n，找到多少就处理多少行；找不到就等下一次 EPOLLIN 再来。

对于发送端（客户端）：
如果客户端调用 send("HELLO\n")，这个数据立刻进入内核发送缓冲区，不关换行符的事，也不关缓冲区满不满的事（只要缓冲区没满就立即发，满了就阻塞）。

如果客户端调用 send("HELLO") 且后面没发 \n，服务端会一直等待，直到客户端发来 \n 或连接断开。

4. 总结
换行符不决定什么时候发送，而决定的是**业务逻辑什么时候处理**
