## handle_login

### 双重锁

#### 为什么？

本地内存：**高速索引**，系统受到客户端命令不可能每一次都查Redis,延迟高压力大，本地内存中存储tcpconnection,实现**同机转发**

Redis：**跨进程互斥锁**，如果有多个服务器，但是本地内存是隔离的。Redis作为中央的存储，记录serverid,保证全局唯一登陆

二者要同时满足

#### 步骤

1.   **本地站位**：先在本地哈希表注册用户名
2.   **远程抢锁**：执行 Redis 命令 `SET key username NX EX ttl`，如果返回成功，那么这个键没有注册，如果失败，那么用户已经注册
3.   **回滚**：如果第二步失败，那么系统立刻执行第一步的逆操作，将本地哈希表中数据删除

### 后台续期

#### 为什么需要？

因为在redis中，键是有过期时间的

如果serverA崩溃，进程终止，那么这个用户名会在redis中被锁死，但是TTL保证了一定时间的自动释放

逻辑：只要ServerA活着，必须不断发送`EXPIRE key ttl` 命令，告诉Redis活着，重置倒计时

## handle_private_message

### 双重锁

#### 业务事务原子性

临界区中必须同时包含`direct_message_policy_.evaluate`（查关系）和 `add_private_message_with_delivery`（写消息表）

##### 为什么？

1.   线程A：执行 `evaluate`，查到“双方是好友且未屏蔽”，获得允许发消息
2.   线程B：成功获取数据库写锁，执行了“删除好友”或“拉黑”操作，并提交事务
3.   线程A：执行 `add_private_message_with_delivery`，将消息写入消息表

导致消息表中留下了一条“**发送者与接收者已经不是好友**”的孤儿私聊记录，这条数据就这么留在了消息表中成为哦飞舞消息

##### 怎么做？

-   **任何修改好友关系的操作**（删除好友、拉黑、解除拉黑）**必须获取同一把锁**。
-   **任何发私聊的操作**（查关系+写消息）**也必须获取同一把锁**。

#### 延时重检

锁在 `add_message`（数据库写入）完成后**立即释放**，随后代码序列化消息、查找在线用户、准备TCP Payload。**这中间是有一段时间的**

##### 为什么？

1.   锁中，A向B发消息，成功写入MySQL
2.   锁释放，服务器准备通过TCP将消息推送给B的在线连接
3.   此时，B通过另一个API请求拉黑了A，MySQL中的关系表已更新
4.   服务器此时调用 `is_friend_blocked` 进行第二次查验

**直接丢弃本次TCP实时推送**，但是消息仍然在消息表中存在。即使实时推送被跳过，B下次主动拉取离线消息（或客户端刷新收件箱）时，依然能从数据库中精准获取这条消息。

为的就是在查完数据到写入消息过程中，防止数据被别的线程改掉

## handle_group_message

### 数据拷贝

`database_.list_group_member_usernames` 在 `handle_group_message` 执行的第一时间被调用，将返回的列表存入 member,后续又将member中成员赋值到recipients中

>   也就是说，我们把消息要发送的一瞬间的数据库群组成员保存了下来

有什么好处呢？

首先，很容易就能想到，这样不用我们每次都去数据库查信息

其次，避免发生冲突，例如A给C群组中发消息，下一秒，B退出群聊，那么A还是会把消息发出去，后续不管什么操作都影响不了这条消息的投递范围——消息属于它被c创建的时刻

### 异步回调

>   业务消息能否执行，取决于网络数据是否真的可以发送出去

其实这个函数很简单，只需要先把消息写入MySql做数据持久化，然后将消息塞进每一个对象的发送队列就好了

在这里，我们把**将 Redis/MySQL 的写入延迟到回调中**，那么主业务线程就不会因为网络IO或者数据库更新而拖慢

而这个回调，是在TcpConnection把**数据成功写入操作系统发送缓冲区之后**才会触发，因为send是非阻塞的，所以说，如果数据只是拷贝进去发送缓冲区，但是还没有发送到网卡上，此时不能立刻在数据库中减去已接受人数，万一客户端突然掉线，用户没有接收到消息但是计数已经减去1,双方状态混乱

我们把数据库的操作写入回调为的就是消息到底有没有到socket这个时机的选择

## handle_file_end+ handle_file_resume_request

### 文件顺序传输

#### 有什么作用?

```c++
handle_file_begin_private
        ↓
handle_file_chunk
        ↓
handle_file_end
```

原本的TCP是流式传输，但是接收到的可能顺序混乱之类的

在代码中，把数据分割成一个一个的块CHUNK传输，服务器还维护着一个session.upload，代表服务器目前已经成功接收并写入了多少字节

而每一个CHUNK传输之前，都会检验上传偏移量和本地成功写入多少字节是否相等

```
offset == received_size
```

相等之后才向服务器缓冲区写入。这样就解决了传输顺序的问题

```
0       4096       8192
|---------|----------|
  已收到       没收到
```

还解决了服务器已经接收了一部分但是客户端依旧从偏移量为0开始上传

解决了**乱序，重复，跳跃**三个问题

#### 怎么实现?

我们在应用层自定义一个协议

```
Chunk:
{
    offset,
    length,
    data
}
```

服务器规定``offset == received_size`

### handle_file_end

#### 权限检查

当用户A给用户B传输一个50G的文件的时候,

这是第一次检验:服务起检查AB之间是好友,可以传输文件

开始传输文件,如果传输到20G到.part中

突然进行第二此检验:发现**用户B删除或者屏蔽用户A的好友**,怎么办???

正确做法是这个文件一定不能传输过去,并且已经传输的20G也要删除,也就是说

>   "开始时允许"不代表"结束时允许"

#### 怎么实现?

在这个函数中在加一条

```c++
direct_message_policy_.evaluate(...)
```

### handle_file_resume_request

#### 连接生命周期

当服务器给客户端发送文件的时候,可能会出现说,文件线程还在运行,但是客户端已经断开连接了

```
网络线程
   ↓
创建异步发送任务
   ↓
文件线程
   ↓
读取文件
   ↓
发送数据
```

我们不能简单的认为connection永远存在,客户端随时都有可能会断开的,所以我们会使用weak_ptr

#### 怎么实现?

我们使用``wake_ptr.lock()`:

​     如果连接还存在,那么得到``shared_ptr`

​     如果连接不存在,那么得到nullptr

我们在此处也不能使用shared_ptr,因为shared_ptr会保证这个对象暂时不会销毁

但是weak_ptr是连接存在就使用,连接不存在就不使用

之后我们要对这个线程或者是这个已经发送的文件进行处理,**不能直接在文件线程上erase**

因为可能文件线程和网络线程都在对同一个容器进行操作,会出现数据竞争,所以我们要使用回调,文件线程上调用`queueInLoop`,让网络线程对其进行处理-----跨线程切回事件循环



### 总结

这是三个重要的思想

1.   用 `offset == received_size` 保证数据传输的顺序和一致性
2.   用 `handle_file_end` 的二次 `policy.evaluate()` 解决“上传过程中权限发生变化”的时间窗口问题
3.   用 `weak_ptr + lock() + queueInLoop()` 解决“后台文件线程”和“网络线程”之间的对象生命周期与线程安全问题





## detach_active_upload



### 优雅关闭

析构顺序很重要

```c++
ChatServer 析构
      │
      ├── 1. heartbeat_manager_.stop()
      │       └── 防止关闭过程中继续产生/处理新的连接活动
      │
      ├── 2. file_transfer_service_.stop()
      │       └── 停止文件传输相关线程/任务
      │
      ├── 3. stopping_ = true
      │       └── 唤醒 presence_refresh_thread_
      │
      ├── 4. 清理 Redis 中的在线状态
      │
      └── 5. detach_active_upload(...)
              │
              └── 不删除磁盘上的 .part / .resume.pb
```

核心的原则是---先阻止新的活动进入系统,然后是停止正在处理的业务,最后清理外部状态

### 断点续传

当服务器析构了,那么内存中的数据都清楚了,那么断点续传怎么实现呢?

```c#
server/tmp/
    ├── <token>.part
    └── <token>.resume.pb
```

此时我们是这样做的

上传任务的"活跃运行状态"在内存中和服务器处于一个生命周期,但是"恢复状态"保存在磁盘中

也就是说,当服务器断开又重联的时候,接受客户端上传的文件的时候,会先看`.part`&`.resume.pb`存在与否,如果以前有人上传过,那么就接着上传

>   状态保留在磁盘,运行在内存
